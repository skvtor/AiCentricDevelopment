Assumptions  
Практика показывает:

- за конечное число итераций “скажи AI что надо сделать \-\> проверь что оно сделало \-\> скажи что надо сделать далее \-\>....” можно получить достойный результат.  
- качество результата коррелирует с качеством постановки задачи.

AI достойно справляется с тактическим написанием кода (а масштабах функций \\ алгоритмов) \-\> стало быть \-\> при качественной декомпозиции “стратегической задачи” (в масштабах системы \\ модуля) на составные тактические, AI имеет шансы справляться и с ними.

При решении “стратегических задач” AI наполняет свой контекст информаций о проекте на лету, исследуя существующий код по зависимостям \-\> качество этого исследования критично для решения стратегической задачи \-\> улучшая качество наполнения контекста (качество осведомленности LLM) мы повышаем шансы на удовлетворительный результат.

Фокус на:  
“качественное наполнение контекста” \-\> вместо исследования проекта на лету \- предоставлять pre-cooked описание кода, которое включает:  
	“Module” \- стратегическая единица кода. Группа классов, сгруппированная по функциональной области, “спрятанная” за публичным интерфейсом, как единственным способом использования Модуля.   
Модуль имеет описание ответственности (ей) (какие задачи решает модуль).   
Модуль имеет поведение??? (TBD: залинковать на SRS\\feature requirements\\feature crumbs).   
Модуль имеет описание публичного интерфейса (описание методов, их предназначений, входных выходных параметров).  
Модуль описывает свои зависимости от других модулей.  
Модуль имеет интеграционные тесты \- фиксирующие поведение.  
Модуль включает в себя набор связанных code blocks.

	“Code block” \- в простейшем случае \- это одна функция, или в более сложных случаях \- группа функций, имплементирующих конкретныцй алгорит\\ответственность, лишь одна функция является точкой входа в блок, все другие функции блока не вызываются извне блока напрямую а лишь через точку входа. По сути мы говорим, что “Code block” это подграф code map (построенной для вызовов функций) соединенный шарниром с остальным графом code map.   
Code block имеет описание ответственности (какую задачу (одну\!) решает этот блок).   
Code block имеет поведение??? (TBD: залинковать на SRS\\feature requirements\\feature crumbs).   
Code block имеет описание точки входа  (название функции и ее входных\\выходных параметров).  
Code block описывает свои зависимости от других Code blocks.  
Code block имеет unit тесты \- фиксирующие поведение (1 feature crumb \=\> 1 тест)
